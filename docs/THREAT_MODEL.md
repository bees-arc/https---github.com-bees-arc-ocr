# Identity Onboarding Lab — Threat Model

Version: 1.0  
Date: 7 October 2026

## 1. Threat Actors & Asset Identification

### Assets to Protect:
- **Applicant Identity PII**: Full name, contact details, date of birth, home address, employment details.
- **Biometric Evidence**: National identity card scans, portrait crops, live video recordings.
- **Institutional Decision Integrity**: Prevention of unauthorized auto-approval, fraudulent bypass of checks, or reviewer impersonation.
- **Audit Logs**: Evidence chain of custody for compliance and regulatory reporting.

### Potential Adversaries:
- **Malicious Applicants / Fraudsters**: Attempting identity theft, replaying old videos, presenting synthetic/printed images (presentation attacks), or manipulating client-side state.
- **Rogue Reviewers**: Attempting unauthorized approvals or viewing evidence without justification.
- **Compromised Network / MitM**: Attempting to intercept session tokens or unencrypted media uploads.
- **Internal Service Attackers**: Attempting path traversal via upload storage keys.

---

## 2. Threat Analysis & Mitigations

| Threat | Attack Vector | Architecture Mitigation |
| :--- | :--- | :--- |
| **Client-Side State Tampering** | Manipulating browser network responses to claim `PASS` on biometric checks. | All checks, scoring, and decisions are executed and enforced exclusively on the Java backend. Client-reported results are ignored. |
| **Liveness Replay Attack** | Injecting a pre-recorded video or looping virtual camera. | Nonce and random challenge steps (e.g. turn-left, blink) are generated cryptographically per attempt on Java with a 90s expiry window. Nonce is single-use and invalidates on consumption. Decoded duration and optical flow are verified server-side. |
| **Document Substitution / Stale Results** | Uploading an NIC, getting face comparison, then replacing the NIC with another person's card. | Every new document or biometric upload increments the aggregate generation counter. Any change to NIC invalidates subsequent checks. Late worker callbacks with stale generation tokens cannot alter the current decision. |
| **Path Traversal via Storage Key** | Client or worker providing `../../etc/passwd` or absolute file path to read/write arbitrary files. | File storage keys are opaque UUIDs generated by Java. File resolution strictly prepends the private storage root and validates canonical path containment. Arbitrary client-provided filenames are rejected. |
| **Database Compromise & PII Leak** | Exfiltration of database backups or SQL dumps. | PII fields and raw extraction values are encrypted at rest with AES-256-GCM. NIC lookup uses keyed HMAC with a secret stored outside the database. |
| **Unauthorized Evidence Peeking** | Reviewers or external users guessing media URLs. | Evidence is never stored in public directories or served statically. Media access is routed through an authenticated backend streaming endpoint that verifies reviewer assignment and records an audit log entry. |
| **Denial of Service via Media Flooding** | Submitting gigabyte-sized files or decompression bombs to exhaust server memory. | Strict file size enforcement (10 MiB for NIC images, 30 MiB for videos), decoded resolution cap (25 megapixels), decoded video duration cap (20 seconds), and stream limits before decoding. |
| **Replay of Idempotent Requests** | Rapid double-clicking on application submission causing duplicate actions. | `Idempotency-Key` header bound to actor ID, route, and request body hash. Repeated submissions return the cached safe response. |
